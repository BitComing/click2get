# Click2Get 技术方案 v1

> 剪贴板捕获式笔记工具 · Windows 桌面端 · 低内存

---

## 1. 需求拆解

| # | 需求 | 技术含义 | 隐含约束 |
|---|---|---|---|
| R1 | Windows 桌面应用，内存占用小 | 不能有常驻浏览器内核；单进程；空闲几乎不耗 CPU | 排除 Electron；Tauri/WebView2 需压测 |
| R2 | 开启监视后，所有文字复制、图片复制自动写入同一篇笔记 | 常驻剪贴板监听（事件驱动，非轮询）+ 追加式写入 | 误捕、隐私（密码库）、自捕获循环、无限增长 |
| R3 | 编辑页支持插入图片 | 需要在文档流里渲染图片，可查看大图 | 图片是**内存杀手**，必须做缩略图+LRU |

**一句话结论**：这个产品的本质不是"富文本编辑器"，而是**一条由"N 个复制片段"组成的追加流**。
认清这一点，编辑器的复杂度会下降一个数量级——这是本方案所有取舍的出发点。

## 2. 技术选型

### 2.1 候选对比

| 方案 | 典型常驻内存 | 开发成本 | 插图编辑器 | 结论 |
|---|---|---|---|---|
| Electron | 250–450 MB | 低 | 现成（ProseMirror） | ❌ 违背 R1 |
| Tauri 2 + WebView2 | 120–200 MB（3+ 进程） | 低 | 现成（ProseMirror/Lexical） | ⚠️ 备选 |
| **Rust + egui/eframe（原生自绘）** | **30–60 MB（单进程）** | 中 | 需自建块式视图 | ✅ **推荐** |
| Rust + Win32 + RichEdit/OLE | 15–30 MB | 高 | 痛苦（ITextServices） | ❌ 投入产出比差 |
| .NET WPF | 70–100 MB | 中 | RichTextBox 一般 | ❌ 本机无 SDK |

> 内存数字是工程预期区间，M0 阶段会实测校准后再定稿。

### 2.2 推荐栈

```
UI 渲染     eframe 0.37 / egui 0.37（glow 后端，原生 OpenGL，无 WebView）
窗口/循环   winit（随 eframe） + tray-icon
剪贴板监听  windows 0.62（直接调 Win32：AddClipboardFormatListener）
剪贴板读写  arboard 3.7（读文本） + 自写 Win32 DIB/PNG 解码
图像处理    image（解码/编码/缩略图）
存储        rusqlite 0.41（bundled，静态编译 SQLite）+ FTS5
打包        cargo-wix / NSIS
```

**为什么不用 Tauri**：WebView2 至少要拉起 browser / renderer / GPU 三个进程，
空窗口基线就在 100 MB 以上，和我们"内存小"的第一需求正面冲突。
它唯一的大优势是现成的富文本编辑器——而第 3 节的块式模型让这个优势不再必要。

## 3. 核心设计决策

### 决策一：文档 = 块流（Block Stream），不是富文本

一次复制 = 一个块。块之间互相独立，不做行内混排。

```rust
enum Block {
    Text  { id, ts, source_app, body: String },   // 纯文本 / 轻 Markdown
    Image { id, ts, source_app, hash, w, h },     // 引用磁盘文件
    Rule  { ts },                                 // 时间分隔线（可选）
}
```

好处：
- 编辑器不需要 rope、不需要 span 样式表、不需要富文本 undo 栈
- 渲染可以**虚拟滚动**（只画可见块），内存与笔记长度无关 ← 直接服务 R1
- 追加是 O(1)，剪贴板写入永不卡顿
- 图片天然是"独立一块"，不需要处理行内图片的排版/对齐/换行

代价：跨块选择、跨块复制、行内加粗都不支持。对"收集碎片"的场景可接受。

> 若后续确实要富文本：在块内引入 Markdown 子集（`**bold**`、`` `code` ``、链接），
> 用 `egui` 的 `LayoutJob` 做行内样式，不需要推翻模型。

### 决策二：图片两份文件 + 内容寻址

```
%LOCALAPPDATA%\Click2Get\
  app.db                                      # SQLite (WAL)
  images\ab\cd\<sha256>.png                   # 原图
  images\ab\cd\<sha256>.thumb.png             # 长边 ≤ 512 缩略图
```

- **捕获时立刻生成缩略图**（在工作线程里），列表页永远只解码缩略图
- 原图只在"双击查看大图"时才解码，关闭即释放
- 按 SHA-256 内容寻址 → 同一张图复制 10 次只占一份磁盘
- 用文件而非 BLOB：操作系统页缓存帮我们管内存，SQLite 不需要把 8 MB 的图读进堆

### 决策三：剪贴板监听用独立线程 + 隐藏窗口

不走轮询（轮询吃 CPU 且快慢都不对），用 Win32 推送：

```
[隐藏窗口线程]                         [UI 线程 (eframe/winit)]
CreateWindowExW (message-only)
AddClipboardFormatListener(hwnd)
  └─ WM_CLIPBOARDUPDATE
       ├─ 过滤（见 4.2）
       ├─ 解码 + 缩略图 + PNG 落盘
       └─ mpsc ──────────────────────► 收到 Capture 事件
                                         ├─ INSERT 到 SQLite
                                         ├─ 追加 Block 到内存模型
                                         └─ ctx.request_repaint()
```

放独立线程的三个理由：大图 PNG 编码是几十毫秒级的活，不能卡 UI；
剪贴板读取可能因对方程序占用而需要重试；
UI 线程的 winit 事件循环不必掺和 Win32 子类化。

## 4. 剪贴板捕获细节（最容易踩坑的部分）

### 4.1 读取优先级

`OpenClipboard` 需带退避重试（对方程序可能正持有），3–5 次 × 20 ms。

1. **排除格式检查**（必须先做）
   - `ExcludeClipboardContentFromMonitorProcessing` / `Clipboard Viewer Ignore`
     → 密码管理器（1Password / KeePass / Bitwarden）会置位，**直接跳过，不记录**
   - 自定义格式 `Click2GetOwned` → 我们自己写剪贴板时加的标记，防止自捕获循环
2. **图片**：优先注册格式 `PNG`（Chrome / Edge / Firefox / 截图工具都给这个）
   → 否则 `CF_DIBV5` / `CF_DIB`，手动解析 `BITMAPINFOHEADER` + 像素，
   注意 32bpp 的**预乘 alpha** 与 `BI_RGB` 下 alpha 通道常为 0 的兼容处理
3. **文本**：`CF_UNICODETEXT`
4. **文件**：`CF_HDROP` → v1 先忽略（或存为路径列表文字块），避免误捕拖拽

### 4.2 过滤规则

| 规则 | 目的 |
|---|---|
| 内容 hash 与上一条 block 相同 → 跳过 | 同一内容重复复制不产生噪音 |
| 文本长度 < 2 或全空白 → 跳过 | 过滤误触 |
| 文本 > 1 MB / 图片 > 20 MB / 边长 > 8000px → 记录但不预览 | 防内存尖峰 |
| 全局开关（托盘 + 热键）暂停 | 临时处理敏感信息 |
| 排除进程白名单 | 可选：某些程序复制永不记录 |

### 4.3 必须提供的逃生口

自动捕获一定会有"多记了"的时刻，所以：
- **撤销上一条捕获**（`Ctrl+Shift+Z`）：删掉最近一个 block
- 托盘菜单可暂停 / 恢复 / 一键清空今日
- 每个块显示来源应用名（`GetForegroundWindow` → 进程名），便于事后判断

## 5. 编辑器实现要点

| 能力 | 实现 |
|---|---|
| 虚拟滚动 | 每块缓存高度（文本 galley 缓存 / 图片按宽高比换算），只布局可见区 ±5 屏 |
| 图片显示 | `egui::Image` + 纹理句柄；纹理缓存 LRU，预算 48 MB，滚出即释放 |
| 查看大图 | 覆盖层解码原图，关闭时 drop 掉 `ColorImage` |
| 编辑文本块 | 每块独立 `TextEdit::multiline`，点击进入编辑态，失焦自动保存（防抖 500 ms） |
| 插入图片 | ① 剪贴板自动；② 手动 `Ctrl+V`（粘贴即插块）；③ 拖拽文件 / 文件对话框 |
| 删除 / 排序 | 块尾菜单删除；排序 v1 先不做（拖拽会引入大量状态） |
| 搜索 | FTS5 + **trigram 分词器**（`unicode61` 不切中文，必须用 trigram） |
| 导出 | 流式写 `note.md` + `assets/`，图片逐个拷贝，不整体读入内存 |

### 中文字体（必做，否则全是豆腐块）

egui 内置字体无 CJK。直接读 `C:\Windows\Fonts\msyh.ttc` 会常驻约 19 MB，
不符合内存目标。做法：用 fonttools 子集化一个 Noto Sans SC
（常用 3500 字 + 拉丁 + 标点），约 2–3 MB 打进二进制。

## 6. 内存控制清单（R1 的落地）

| 手段 | 效果 |
|---|---|
| 原生渲染，无 WebView | 省掉 100 MB+ 的多进程开销 |
| 虚拟滚动 + 分页查询（keyset by `ord`） | 内存与笔记条数解耦 |
| 缩略图两级缓存 + LRU 48 MB 上限 | 500 张图的笔记，纹理内存仍 ≤ 48 MB |
| 按显示尺寸解码，不在内存留原图 | 单张 4K 原图省 30 MB |
| SQLite `PRAGMA cache_size=-2000`（2 MB） | 默认值是 -2000KB，显式固定住 |
| 窗口隐藏到托盘时清空纹理缓存 | 从 60 MB 回落到 ~25 MB |
| `lto = true`, `panic = "abort"`, `strip = true` | 二进制 ~8–12 MB |

**预期内存预算（待 M0 实测校准）**

| 场景 | 目标 |
|---|---|
| 托盘常驻、窗口隐藏 | 22–30 MB |
| 窗口打开、空笔记 | 35–45 MB |
| 窗口打开、滚动中（20 张缩略图） | 50–65 MB |
| 查看一张 4K 原图 | 瞬时 +25 MB，关闭即回落 |

> 不做 `EmptyWorkingSet` 强制回收：它会把页面刷到磁盘，下次交互明显卡顿，
> 属于"任务管理器好看但体验变差"的假优化。提供开关，默认关。

## 7. 数据模型

```sql
PRAGMA journal_mode=WAL;
PRAGMA cache_size=-2000;

CREATE TABLE notes(
  id INTEGER PRIMARY KEY, title TEXT,
  created_at INTEGER, updated_at INTEGER
);

CREATE TABLE blocks(
  id INTEGER PRIMARY KEY,
  note_id   INTEGER NOT NULL REFERENCES notes(id),
  ord       INTEGER NOT NULL,          -- 笔记内序号，追加即 +1
  kind      TEXT    NOT NULL,          -- text | image | rule
  created_at INTEGER NOT NULL,
  source_app TEXT,
  text      TEXT,                      -- kind=text
  image_hash TEXT, image_w INTEGER, image_h INTEGER, image_bytes INTEGER,
  content_hash TEXT NOT NULL           -- 去重
);
CREATE UNIQUE INDEX idx_blocks_ord  ON blocks(note_id, ord);
CREATE INDEX        idx_blocks_hash ON blocks(note_id, content_hash, created_at DESC);

CREATE VIRTUAL TABLE blocks_fts USING fts5(
  text, content='blocks', content_rowid='id', tokenize='trigram'
);
```

单篇笔记（`note_id = 1`）满足当前需求，但 schema 保留多篇能力，未来不用迁移。

**无限增长的处理**：单篇笔记按天自动插 `rule` 分隔块；超过 N 条时提示
"归档到新笔记"，旧笔记只读。不做自动删除（数据丢失风险 > 收益）。

## 9. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **egui 的 IME（中文输入）体验** | 高 | M0 就打中文验证；egui 0.37 已支持 winit IME 事件，但候选框定位/hit-test 仍需实测。不过关则切 Tauri |
| CF_DIB 的 alpha 解析错误（黑底/透明） | 中 | 只信 `PNG` 格式，DIB 作为兜底；alpha 全 0 时按不透明处理 |
| 超大图瞬间内存尖峰 | 中 | 捕获阶段就限制边长，先缩后存 |
| 误捕敏感内容（密码/身份证） | 高 | 尊重排除格式 + 随时暂停 + 来源应用可见 + 撤销上一条 |
| 自捕获循环（在本应用内复制） | 中 | 写剪贴板时打 `Click2GetOwned` 标记格式 |
| 剪贴板被独占导致读取失败 | 低 | 退避重试，失败仅记日志不重试到底 |
| 多显示器 / DPI 150% 下图片模糊 | 低 | 纹理按 `pixels_per_point` 放大生成 |

## 10. 待你拍板

1. **技术栈**：接受 Rust + egui 自绘（内存达标、编辑体验需自建），
   还是接受 120–200 MB 换 Tauri 的成熟编辑器？—— 我建议前者。
2. **图片存储**：文件式（本方案，省内存、可去重）vs 全部塞进 SQLite 单文件
   （备份/迁移只有一个 db 文件）。建议前者，导出 zip 做备份。
3. **格式保留**：浏览器复制的加粗/超链接/列表要不要保留？
   v1 建议不保留（纯文本块），v2 再解析 `CF_HTML`。
4. **捕获粒度**：Ctrl+C 全量捕获必然有噪音，是否要"只在按住某修饰键时才捕获"的静默模式？
